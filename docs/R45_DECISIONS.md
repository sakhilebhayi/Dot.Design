Append-only. Format: `D-n (agent, date): decision. Why.` On merge conflicts keep both sides.

D-1 (coordinator, 2026-11-09): Workspace tenancy = Jetstream Team; projects stay private to the owner by default, `visibility=team` shares with the workspace. Why: matches InfoDot team sync and the brief's business-workspace model without breaking existing owner-only rows.
D-2 (coordinator, 2026-11-09): Editor is vanilla ES modules built by Vite with ONE SVG renderer for screen and export. Why: export parity, no Alpine/Livewire start-order coupling, testable pure modules.
D-3 (coordinator, 2026-11-09): Document schema lives in resources/design/document-schema.json, read by PHP and JS. Why: one source of truth, no drift.
D-4 (coordinator, 2026-11-09): No real-time co-editing, background removal, social publishing, stock photos or MP4 export; each is stated in the report as not built. Why: no honest implementation is possible on the shared host / without licences or APIs.
D-5 (coordinator, 2026-11-09): schema bind_key pattern is ^[a-z][a-z0-9_]{0,39}$ so photo_1..3 are valid (found by business agent, D-402).
D-400 (business, 2026-11-10): Brand kits and templates use a tiny local trait `App\Models\Concerns\ScopesToWorkspace` (owner OR member of the row's team, 404 otherwise); `DesignTemplate` overrides `constrainToWorkspace()` (curated published are visible to all, operators see all curated, team templates only to the team, user templates only to the owner). Why: the backend agent builds `HasWorkspaceScope` on another branch; the seam is one `use` line to swap at merge.
D-401 (business, 2026-11-10): `bootstrap/app.php` renders JSON for `design/*` requests that send `Accept: application/json` (was only `api/*`), so the studio endpoints answer 401/403/404/422 as JSON instead of redirects. One existing test (`DesignAssetUploadTest::test_guests_cannot_upload`) now expects 401 instead of a redirect for a JSON caller. Why: `shouldRenderJsonWhen` ignored the Accept header, so every validation error on a JSON endpoint came back as a redirect.
D-402 (business, 2026-11-10): PROPOSED schema change (not applied, schema is not mine): `value_types.bind_key` must become `^[a-z][a-z0-9_]{0,39}$`. The current `^[a-z_]{1,40}$` has no digits, so the required slot keys `photo_1..photo_3` are invalid. `TemplateChecker` already uses the proposed pattern. The backend sanitiser must use it too or it will strip photo binds.
D-403 (business, 2026-11-10): Format catalog px size is canvas px at 72 dpi (A4 = 595 x 842, business card ZA = 255 x 156); projects made from a brief store width/height in that px with unit `px`; print export multiplies by `dpi_print / 72`. Why: one coordinate system for the engine; the catalog keeps real mm/in for people and printers.
D-404 (business, 2026-11-10): Templates never carry pictures (`asset_id` and `background.asset_id` must be empty; save-as-template strips them) and `TemplateChecker` REFUSES unknown keys, wrong enums and out-of-range numbers instead of repairing them. Why: templates are authored content (a typo is a bug to fix) and a team template must not leak one member's upload into another's design.
D-405 (business, 2026-11-10): Brand application is driven only by an element's `tokens` map (color, fill, stroke_color, shadow_color, font). At template instantiation brand colours/fonts apply only with `apply_brand` plus a kit; without it tokens stay as inert metadata (literal colours render). `BrandService::applyUpdate` needs an explicit selection (`items` keys or `all: true`), snapshots first, rewrites only the selected token-referenced props, bumps the page `revision`, and records `brand_version` only when nothing is left to apply; a partial apply keeps the project marked outdated; `dismiss` acknowledges the version without touching the design. Why: never-silent rule; an open editor must see a revision conflict, not be overwritten.
