# R-45 decisions log

Append-only. Format: `D-n (agent, date): decision. Why.` On merge conflicts keep both sides.

D-1 (coordinator, 2026-11-09): Workspace tenancy = Jetstream Team; projects stay private to the owner by default, `visibility=team` shares with the workspace. Why: matches InfoDot team sync and the brief's business-workspace model without breaking existing owner-only rows.
D-2 (coordinator, 2026-11-09): Editor is vanilla ES modules built by Vite with ONE SVG renderer for screen and export. Why: export parity, no Alpine/Livewire start-order coupling, testable pure modules.
D-3 (coordinator, 2026-11-09): Document schema lives in resources/design/document-schema.json, read by PHP and JS. Why: one source of truth, no drift.
D-4 (coordinator, 2026-11-09): No real-time co-editing, background removal, social publishing, stock photos or MP4 export; each is stated in the report as not built. Why: no honest implementation is possible on the shared host / without licences or APIs.
D-5 (coordinator, 2026-11-09): schema bind_key pattern is ^[a-z][a-z0-9_]{0,39}$ so photo_1..3 are valid (found by business agent, D-402).
D-400 (business, 2026-11-10): Brand kits and templates use a tiny local trait `App\Models\Concerns\ScopesToWorkspace` (owner OR member of the row's team, 404 otherwise); `DesignTemplate` overrides `constrainToWorkspace()` (curated published are visible to all, operators see all curated, team templates only to the team, user templates only to the owner). Why: the backend agent builds `HasWorkspaceScope` on another branch; the seam is one `use` line to swap at merge.
D-401 (business, 2026-11-10): `bootstrap/app.php` renders JSON for `design/*` requests that send `Accept: application/json` (was only `api/*`), so the studio endpoints answer 401/403/404/422 as JSON instead of redirects. One existing test (`DesignAssetUploadTest::test_guests_cannot_upload`) now expects 401 instead of a redirect for a JSON caller. Why: `shouldRenderJsonWhen` ignored the Accept header, so every validation error on a JSON endpoint came back as a redirect.
D-402 (business, 2026-11-10): PROPOSED schema change (not applied, schema is not mine): `value_types.bind_key` must become `^[a-z][a-z0-9_]{0,39}$`. The current `^[a-z_]{1,40}$` has no digits, so the required slot keys `photo_1..photo_3` are invalid. `TemplateChecker` already uses the proposed pattern. The backend sanitiser must use it too or it will strip photo binds.
D-403 (business, 2026-11-10): Format catalog px size is canvas px at 72 dpi (A4 = 595 x 842, business card ZA = 255 x 156); projects made from a brief store width/height in that px with unit `px`; print export multiplies by `dpi_print / 72`. Why: one coordinate system for the engine; the catalog keeps real mm/in for people and printers.
D-404 (business, 2026-11-10): Templates never carry pictures (`asset_id` and `background.asset_id` must be empty; save-as-template strips them) and `TemplateChecker` REFUSES unknown keys, wrong enums and out-of-range numbers instead of repairing them. Why: templates are authored content (a typo is a bug to fix) and a team template must not leak one member's upload into another's design.
D-405 (business, 2026-11-10): Brand application is driven only by an element's `tokens` map (color, fill, stroke_color, shadow_color, font). At template instantiation brand colours/fonts apply only with `apply_brand` plus a kit; without it tokens stay as inert metadata (literal colours render). `BrandService::applyUpdate` needs an explicit selection (`items` keys or `all: true`), snapshots first, rewrites only the selected token-referenced props, bumps the page `revision`, and records `brand_version` only when nothing is left to apply; a partial apply keeps the project marked outdated; `dismiss` acknowledges the version without touching the design. Why: never-silent rule; an open editor must see a revision conflict, not be overwritten.
D-406 (business, 2026-11-10): Seams for other agents: `App\Contracts\Design\VersionSnapshotter` and `ActivityRecorder` with Null defaults bound by `bindIf` in `StudioBusinessServiceProvider`. Applying a brand update reports `snapshot_taken: false` when only the null snapshotter is bound. Why: honest about missing undo until the backend VersionService is bound.
D-407 (business, 2026-11-10): `design_projects` gets `format_key, template_id, brief, brand_kit_id, brand_version` through a guarded migration (each column only if absent; architecture lists the same columns for the backend migration), with no foreign keys on `brand_kit_id`/`template_id`. `ProjectMeta` reads/writes them via the query builder, and canvases are inserted via the query builder with explicit JSON, so the shared `DesignProject`/`DesignCanvas` models are untouched and a later `brief` cast cannot double-encode.
D-408 (business, 2026-11-10): `design:seed-templates` reads `database/templates/*.php` (a file returns one definition, a list, an object with `definitions()`, or a Closure; files starting with `_` or an upper-case letter are helpers and never loaded), upserts curated templates by slug keyed on a content hash (unchanged = untouched, changed = version+1, usage kept), refuses invalid ones with all their errors and still loads the valid ones, exits 1 if anything was refused or a slug clashes with a saved template, `--check` writes nothing, `--retire-missing` retires curated rows whose file is gone.
D-409 (business, 2026-11-10): `BriefRecommender` is fully deterministic: weighted points for purpose, kind position, size, style, industry, own template, popularity and usage (weights are constants in the class and documented), ties by popularity then slug, a plain-language reason per entry, topped up with general starting points only when fewer than 4 templates fit. Industry is guessed from whole-word keywords in config.
D-410 (business, 2026-11-10): `BrandPalette` (GD only): shrink to 96 px, ignore transparent and edge pixels, popularity clustering on a 5-bit histogram, rank by coverage weighted to saturation, neutrals flagged and placed last, up to five colours with WCAG contrast info and role suggestions. Why: median cut averaged a logo's few flat colours into mud.
D-411 (business, 2026-11-10): What counts as a kit change (version bump): colours, fonts, type styles, guidelines, voice, tagline, website, contacts, and adding/removing/replacing a kit picture. Renaming a kit or changing which kit is default does not. A kit chosen in the brief supplies logo, tagline, website and contact details where the brief gave none (reported as source `brand`), but never colours or fonts unless `apply_brand`.
D-412 (business, 2026-11-10): Validation errors for a brief are keyed by brief field (`details.phone`, `format_key`), not prefixed with `brief.`, so the form can bind them directly. Creation endpoints share the `design-briefs` limiter (60 per minute per user, defined in `StudioBusinessServiceProvider::boot`).
D-600 (integrations, 2026-11-09): Only four integrations are built: Dot.Notify, Dot.Files, the InfoDot membership webhook, and status reporting for the existing sign-in and Analytics. Why: each has a contract read in the sibling code; every other platform has only `GET /user` behind Sanctum, per-person tokens, or no service (docs/R45_INTEGRATIONS.md).
D-601 (integrations, 2026-11-09): Every integration is off by default and needs its flag plus url/secret; adapters sit behind `Contracts\NotificationGateway` and `Contracts\FileVault`; the listener is not even queued while Notify is off. Why: the app must behave identically with all integrations absent (proved in IntegrationsPageTest).
D-602 (integrations, 2026-11-09): Analytics is not extended. Why: Dot.Analytics' `design` catalogue accepts only `projects` and `assets` and silently drops other keys; sending more would look wired and arrive nowhere. The wanted metric names are listed in the doc for Analytics to add.
D-603 (integrations, 2026-11-09): Design notifications carry only the design name, the actor's name, a decision label and a link; never comment text, notes or other addresses; a workspace without an InfoDot company uuid sends nothing. Why: Notify stores uncatalogued `data` unfiltered and files events per company; privacy by construction.
D-604 (integrations, 2026-11-09): Saving to Dot.Files takes an export uploaded from the browser (not a server re-render), verifies the bytes match the format, and requires an explicit `acknowledge` because Dot.Files makes the file visible to the whole business. A repeat save of the same page+format is a new Dot.Files version via `design_file_links` (pointers only). Why: architecture section 3 says exports are produced in the browser; Files visibility ignores the design's own visibility.
D-605 (integrations, 2026-11-09): Event stubs `DesignCommentAdded`, `DesignReviewRequested`, `DesignReviewDecided`, `DesignShared` use plain ids with a documented shape; the backend agent's real classes replace them and the mapping lives in `NotificationPlanner`. `EcosystemMemberRemoved` is mine and lets the backend revoke what a removed person granted. Why: parallel branches; one reconciliation point.
D-606 (integrations, 2026-11-09): The membership webhook route is loaded by `StudioIntegrationsServiceProvider` under the `api` group, guarded by `routesAreCached()`, because routes/web.php loads studio routes inside the auth group. Why: a signed server-to-server call has no user; route:cache stays valid (verified).
D-607 (integrations, 2026-11-09): `design/projects/{project}/dot-files` validates by hand and returns JSON 422 for `expectsJson()`. Why: bootstrap/app.php renders JSON errors only for `api/*`, so the framework's validation redirect would hide errors from fetch().
D-100 (ds, 2026-11-09): Direction is "The Light Table" (DESIGN.md at the repo root, Google design.md format, lint clean). Cool near-neutral paper and ink, ONE hue (process cyan #0A6A91 light, #5CC3EE dark) for selection, focus, links and progress; the primary button is ink on paper, not the accent; the stage (--lt-stage) is a pure neutral grey in both themes. Why: the owner rejected the dark pink SaaS look and the generic reject list (cream+serif+terracotta, near-black+acid accent, hairline broadsheet, four metric tiles, floating cards); a colour-true stage is what a design tool needs; process cyan pairs with the logo's yellow as a print-process story.
D-101 (ds, 2026-11-09): Fonts: Bricolage Grotesque (display) and Atkinson Hyperlegible Next (UI), both SIL OFL 1.1, latin-subset variable woff2 self-hosted in public/fonts/ui/ (licences in LICENSE-fonts.txt), copied from the npm packages @fontsource-variable/bricolage-grotesque 5.3.0 and @fontsource-variable/atkinson-hyperlegible-next 5.3.0 (NOT added to package.json, no runtime dependency). Instrument Sans was tried first and dropped: the Impeccable detector lists it, with Inter, Geist, Space Grotesk, Plus Jakarta Sans and Mona Sans, as a converged default. Neither chosen face is used by another Dot platform.
D-102 (ds, 2026-11-09): Icons are an inline-SVG set (133 icons) read by App\Support\Ui\Icons and drawn by <x-ds.icon>: Lucide 1.70.0 (ISC, licence copied to resources/views/components/ds/icons/LICENSE-lucide.txt) plus 5 drawn here (registration, swatch, artboard, colour-bars, nib). No Material Symbols, no CDN.

D-300 (backend, 2026-11-09): Visibility is a global scope (`HasWorkspaceScope`) and capability checks go through one class (`DesignAccess`) + enum (`DesignCapability`). Why: a forgotten check cannot leak a row; one place to read and change the matrix.
D-301 (backend, 2026-11-09): A workspace admin does NOT see a teammate's private project; visibility = private means owner only (plus explicit grants and the named reviewer of a review). Why: the brief's rule says so, and it is the safer reading.
D-302 (backend, 2026-11-09): Added `design_project_grants` (explicit per-project access for workspace members) and the "named reviewer of a non-cancelled review" implicit grant. D-303 (backend, 2026-11-09): A former member keeps view/export/delete on their own projects only; a deleted workspace leaves projects private to their owners with full control. Why: the leaver must not keep editing in a company they left, but must not lose their own work.
D-304 (backend, 2026-11-09): Added the Jetstream `viewer` role ("Reviewer": view, comment, approve). InfoDot sync maps a `viewer` to it and an ordinary `member` to `editor` (changed `SyncTeamsFromInfoDot::localRole`; the old "viewer falls back to editor" test was rewritten). Why: before, any non-admin non-editor InfoDot member silently became an editor; now only an explicit viewer is read-only.
D-305 (backend, 2026-11-09): Separation of duties: with more than one workspace member nobody reviews or approves their own request; in a one-member workspace the owner reviews their own work. Why: the brief's rule plus the only case where it cannot apply.
D-306 (backend, 2026-11-09): One pending review per project; a review pins a `manual` snapshot "Sent for review" which is promoted to `approved` on approval; a pending review is not made stale by edits, an approved one is. Why: the reviewer decides on exactly what was sent; approval never silently outlives the work.
D-307 (backend, 2026-11-09): Automatic snapshot is of the state BEFORE the save that triggers it, at most every 10 minutes, inside the save transaction. Why: the original is always recoverable and a conflicting save writes nothing.
D-308 (backend, 2026-11-09): The sanitiser has three outcomes (correction counted by kind, 422 field error, rejection 413/422) and materialises all defaults on save; reads are lenient and never write back. Why: the editor can always open an old project, and hostile input never reaches storage.
D-309 (backend, 2026-11-09): The old v1 save route is kept, stays in v1 storage and goes through `PageStore::savePrepared()`. Why: the old editor keeps working while sharing revision, snapshot and review-stale behaviour.
D-310 (backend, 2026-11-09): JSON requests to `design/*` and `s/*` now render JSON errors (401 for a lapsed session instead of a login redirect, `{"message":"Not found."}` for missing rows). Existing test `test_guests_cannot_upload` was updated (401 for JSON, redirect for a browser request). Why: fetch() callers cannot act on an HTML redirect, and the model name must not leak.
D-311 (backend, 2026-11-09): `design_activity` has no foreign keys and is append-only at the model level. Why: deleting a project/user/workspace must not erase or null the audit of it.
D-312 (backend, 2026-11-09): Thumbnail stored as `design_projects.thumbnail_path` on the private asset disk (not `thumbnail_asset_id`); PNG/WebP only, <= 300 KB, re-encoded through GD, served only via a policy-checked route. Why: the brief asked for a path; keeps thumbnails out of the user's asset quota and library.
D-313 (backend, 2026-11-09): Share links are anonymous with no session (StartSession and CSRF excluded on `s/*`), a honeypot field and per-link+visitor throttling; failures all render one 404. Why: no cookie, no enumeration, no stored address.
D-314 (backend, 2026-11-09): Page idempotency keys live in the cache for 24 h per user+project (with a lock), not in a table. Why: short-lived by nature; a lost key only means a retry could create a second page, never data loss.
