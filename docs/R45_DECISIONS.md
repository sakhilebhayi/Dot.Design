# R-45 decisions log

Append-only. Format: `D-n (agent, date): decision. Why.` On merge conflicts keep both sides.

D-1 (coordinator, 2026-11-09): Workspace tenancy = Jetstream Team; projects stay private to the owner by default, `visibility=team` shares with the workspace. Why: matches InfoDot team sync and the brief's business-workspace model without breaking existing owner-only rows.
D-2 (coordinator, 2026-11-09): Editor is vanilla ES modules built by Vite with ONE SVG renderer for screen and export. Why: export parity, no Alpine/Livewire start-order coupling, testable pure modules.
D-3 (coordinator, 2026-11-09): Document schema lives in resources/design/document-schema.json, read by PHP and JS. Why: one source of truth, no drift.
D-4 (coordinator, 2026-11-09): No real-time co-editing, background removal, social publishing, stock photos or MP4 export; each is stated in the report as not built. Why: no honest implementation is possible on the shared host / without licences or APIs.
D-600 (integrations, 2026-11-09): Only four integrations are built: Dot.Notify, Dot.Files, the InfoDot membership webhook, and status reporting for the existing sign-in and Analytics. Why: each has a contract read in the sibling code; every other platform has only `GET /user` behind Sanctum, per-person tokens, or no service (docs/R45_INTEGRATIONS.md).
D-601 (integrations, 2026-11-09): Every integration is off by default and needs its flag plus url/secret; adapters sit behind `Contracts\NotificationGateway` and `Contracts\FileVault`; the listener is not even queued while Notify is off. Why: the app must behave identically with all integrations absent (proved in IntegrationsPageTest).
D-602 (integrations, 2026-11-09): Analytics is not extended. Why: Dot.Analytics' `design` catalogue accepts only `projects` and `assets` and silently drops other keys; sending more would look wired and arrive nowhere. The wanted metric names are listed in the doc for Analytics to add.
D-603 (integrations, 2026-11-09): Design notifications carry only the design name, the actor's name, a decision label and a link; never comment text, notes or other addresses; a workspace without an InfoDot company uuid sends nothing. Why: Notify stores uncatalogued `data` unfiltered and files events per company; privacy by construction.
D-604 (integrations, 2026-11-09): Saving to Dot.Files takes an export uploaded from the browser (not a server re-render), verifies the bytes match the format, and requires an explicit `acknowledge` because Dot.Files makes the file visible to the whole business. A repeat save of the same page+format is a new Dot.Files version via `design_file_links` (pointers only). Why: architecture section 3 says exports are produced in the browser; Files visibility ignores the design's own visibility.
D-605 (integrations, 2026-11-09): Event stubs `DesignCommentAdded`, `DesignReviewRequested`, `DesignReviewDecided`, `DesignShared` use plain ids with a documented shape; the backend agent's real classes replace them and the mapping lives in `NotificationPlanner`. `EcosystemMemberRemoved` is mine and lets the backend revoke what a removed person granted. Why: parallel branches; one reconciliation point.
D-606 (integrations, 2026-11-09): The membership webhook route is loaded by `StudioIntegrationsServiceProvider` under the `api` group, guarded by `routesAreCached()`, because routes/web.php loads studio routes inside the auth group. Why: a signed server-to-server call has no user; route:cache stays valid (verified).
D-607 (integrations, 2026-11-09): `design/projects/{project}/dot-files` validates by hand and returns JSON 422 for `expectsJson()`. Why: bootstrap/app.php renders JSON errors only for `api/*`, so the framework's validation redirect would hide errors from fetch().
